# NETSHIFT Core v2 — State Ownership Audit (working document)

**Purpose:** make it explicit which layer is authoritative for each gameplay property before adding more multiplayer features. The Chunk 1 source-verified matrix below is a static audit of the root `staging` source at the commit named below, not a claim that every browser-state call site has already been migrated or that runtime tests have passed. The full audit and migration remain release gates.

## Rules of ownership

1. PostgreSQL is the authority for persistent identity, money, account credentials, files, software ownership, PvP/NPC outcomes, host stock/claims, router/admin logs, sanctions and leaderboard submissions.
2. The browser may render, animate, collect proposed user input and cache read-only results. It may not decide a successful hack, credit/debit, ownership transfer, ban, cooldown or loot outcome.
3. Every mutation must authenticate the session, check session ownership and target ownership/permissions, validate the request, and apply state changes transactionally where related records must stay consistent.
4. API responses should expose only fields that the current player or public world is allowed to see. Never return password hashes, TOTP secrets, player bank-account secrets, private admin logs or another player's private inventory.
5. Every migration must be additive/idempotent, safe on redeploy, and independently testable against staging. No release step wipes staging or production data.

## Chunk 1 — Source-verified state-ownership audit (2026-10-13)

**Audit basis:** public `staging` branch at commit `06c28e60f348e1b2b1891d00db597180afd4eae0` (`backend email infra`). The reviewed application is the repository-root app: root `render.yaml` runs root `npm install && npm run check` and `npm start`. The repository also contains a nested `netshift-online/` copy with a shorter/different server and client. Do not confuse that nested copy with the root app being audited.

**Evidence standard:** statuses below are based on static inspection of source and test definitions. “Source-verified” means the relevant path is present in code; it does not mean it was integration-tested against PostgreSQL or deployed staging during this chunk. The existing staging checklist contains reports of selected successful staging tests, but those reports are not independently re-run or upgraded to fresh verification here.

### Executive findings

1. **Inventory authority is split.** PostgreSQL `netshift_player_files` plus `/api/core/files` is the canonical file/folder/recycle-bin foundation. However, the legacy browser model (`state.localFiles`, `state.userFoldersV2`, `state.localFileFolders`, `state.recycleBin`, `state.owned`, and `state.archiveSoftware`) remains active and is still mutated by old download, software, archive, drag/drop, reward, infection and restore handlers.
2. **No legacy inventory migration exists in this root staging source.** There is no `/api/core/inventory/migrate-legacy` route, migration ledger, or `lib/legacy-inventory.js` in the root tree. Login restores the generic save and then attempts a canonical file refresh; it does not migrate old inventory arrays into canonical rows.
3. **Canonical inventory views are improved but overall inventory authority is still split.** Chunk 7 maps server-owned files, software and folders into typed collections; Desktop, Downloads, Archive, custom folders and Recycle Bin now render canonical rows using server record IDs. `state.owned`/`state.archiveSoftware` remain compatibility mirrors for existing gameplay functions, and legacy download/freeware/reward/context paths still mutate browser arrays. The browser still has no call site for `POST /api/core/hosts/:slug/download`.
4. **The generic save boundary is now restricted locally.** Chunks 4–5 add a schema-v2 preferences-only server allowlist and matching client protocol. `preferences.lastAddress` is the sole saved preference; protected gameplay state is no longer accepted through the generic save API. Static/helper tests pass, but PostgreSQL and browser integration remain outstanding.
5. **Session ownership must be regression-tested consistently; an earlier read-path concern was superseded by the current middleware.** In the current candidate, `requireAuth` updates `netshift_account_ownership` only where both `user_id` and the current `req.sessionID` match, returning `401 SESSION_REVOKED` if no row matches. Routes using `requireAuth`, including canonical file reads, Recycle Bin reads, profile reads and `GET /api/save`, therefore already pass through this ownership check. Do not add redundant per-route calls without a demonstrated gap. Remaining evidence needs are stale-session/revocation integration tests, response scoping and cache behaviour.
6. **The frontend’s active behaviour is difficult to infer from an isolated source match.** The initial ownership audit counted 495 function declarations, 277 distinct names, 101 redeclared names and 218 declarations beyond the first. Chunks 4–7 add further code, so those numbers are historical baseline measurements, not a current count. Duplicate definitions and end-of-file wrapper assignments mean static markers alone are insufficient evidence of runtime behaviour; test the effective final binding and visible path.
7. **The transactional economy, complete PvP resolution, server-side NPC loop, shared intrusion logs, email delivery and enforced admin MFA remain incomplete.** These belong to later roadmap stages or explicit deferred work; Chunk 1 records their current authority so Stage 1 does not accidentally imply they are complete.

### Concrete mutation and call-path map for Stage 1

- **Canonical file reads:** `GET /api/core/files`, `GET /api/core/files/recycle-bin` (`server.js:1232-1248`) query by the authenticated user ID and run behind `requireAuth`, which validates the active session against `netshift_account_ownership`. The read routes do not need a redundant direct call to `requireSessionOwnership`; still test private response visibility and cache behaviour.
- **Canonical file writes:** create (`server.js:1250-1269`), file edit/move (`1270-1301`), recycle (`1302-1311`), restore (`1312-1325`) and permanent delete (`1326-1335`). These paths use `requireSessionOwnership`; create permits only `file`/`folder`, and edit only permits `file`.
- **Host download:** `POST /api/core/hosts/:slug/download` (`server.js:1336-1364`) is the only current route that adds a `software` item to `netshift_player_files`, but there is no matching `netshiftApi` call in the active client source.
- **Core hydration (updated in Chunk 6 locally):** `netshiftCoreLoadProfile({required:true})` and `netshiftCoreLoadFiles({required:true})` now validate response shapes; the file loader requires explicit arrays for both active files and the Recycle Bin, rejects malformed/duplicate records, and restores its prior client mirrors if mapping/rendering fails. During authentication, the account overlay remains blocking and world sockets/autosaving are not enabled until both required loads succeed. Required reads time out and expose a retry/sign-out path. Optional file refresh failures retain the last confirmed mirror instead of returning a synthetic empty inventory. Stale responses are fenced by account/session-attempt identity so an old account cannot overwrite a new account's browser mirror. These behaviours have static/helper checks only; real browser and PostgreSQL testing remain outstanding.
- **Core-save boundary:** `netshiftSnapshot()` (`4893-4917`) drops browser tabs and filters `localFiles`, `userFoldersV2`, and `recycleBin` entries only when their client-side `_core*Id` marker is present. It still serializes legacy `owned`, `archiveSoftware`, `accounts`, logs, hack/access data and old files/folders. `POST /api/save` (`1043-1110`) accepts that entire `state` object without field allowlisting.
- **Legacy inventory writers:** final `completeNetworkDownloadV11()` near `public/index.html:4627-4655` inserts/replaces `state.localFiles` and `state.localFileFolders` and can call `installSoftwareLocally()`. Software install and ownership logic (`3870s` and repeated declarations later in the script) mutate `state.owned`/`state.archiveSoftware`; context/drag/recycle functions mutate legacy arrays. End-of-file Core wrappers intercept some operations only when `_coreFileId` exists, not the entire old handler family.
- **Legacy economy writers:** browser purchase/transfer/reward/malware/autorenew functions mutate `state.accounts.*.balance` and `state.activity`; no server ledger route backs these actions. Do not migrate these entries as real transactions.
- **Legacy hack/security writers:** browser attack state, logs, infections and NPC timers are modified by the repeated `runSoftware`, `enterBackend`, `runNpcAttackV11`, `activateInfectionV11`, and related functions. Core `/api/world/targets/:slug/breach` is a separate authoritative slice, not a full replacement.

A line-level search across `public/index.html` found 495 top-level function declarations, 277 distinct function names, 101 duplicated names, and 218 declarations beyond the first. Examples: `downloadSoftware` is declared 8 times; `completeNetworkDownloadV11` 8 times; `contextAction` 7 times; `renderExplorerContent` and `runSoftware` 6 times each; `openExplorerWindow` 6 times. **Audit consequence:** a required marker or an early definition cannot prove active behaviour. Future Stage 1 implementation must trace the last declaration plus runtime reassignment, then test the user-visible path. Broad renaming/refactoring is not part of this audit chunk.

### Stage 1 findings to carry into later chunks

1. The approved cutover now retires the old save blob rather than importing legacy inventory into canonical tables. `lib/legacy-save-cutover.js` and `netshift_migration_receipts` implement a one-time reset of `netshift_saves` only; its SQL has not yet been tested against PostgreSQL. No legacy save inventory is imported into `netshift_player_files` by design.
2. Canonical file inventory is a partial implementation, not a unified canonical inventory. Downloads, installed software, Archive and some Recycle Bin operations still use browser-local arrays.
3. Core host downloads are not connected to client UI; the current API's conflict handling must be made loss-safe before it becomes the single delivery path.
4. The legacy whole-state endpoint no longer accepts schema-v1 writes or returns unvalidated stored documents. Chunk 4 adds a schema-v2 preferences-only server writer and revision checks; Chunk 5 updates the frontend; Chunk 6 gates the post-login experience on required profile and active/Recycle Bin inventory reads. This is implemented locally but still requires real browser/PostgreSQL validation; do not deploy this checkpoint as a complete game build.
5. Required first-login hydration now fails closed: errors or malformed payloads leave gameplay and autosaving blocked, with retry/sign-out UI, rather than declaring the inventory empty. Optional file refresh failures preserve the last confirmed canonical mirror. Session-attempt checks prevent delayed old-account responses from overwriting the current account's state. Inventory consistency and legacy writer reconciliation remain open.
6. Current private save/profile/file reads use `requireAuth`, which checks the session against `netshift_account_ownership`; do not add redundant route-level checks without reason. Still verify cache headers, the response visibility matrix and stale-session behaviour in automated/integration tests.
7. Folder and recycle UI models are incomplete for nested folders and software-type preservation. Folder CRUD and canonical software installation need an explicit contract before the old handlers are retired.

## Explicit release blockers

- A malicious client must not be able to set their balance or inventory in `/api/save`.
- No legacy purchase, transfer, cashout or upgrade may claim to debit/credit real money until wired to the authoritative server ledger.
- No attack result may be accepted from client state alone.
- Player A's private bank records and non-public files must not appear to player B.
- Admin routes must require a valid admin role and verified MFA, not merely a role row.
- A multiple-instance Render deployment is not supported until cross-instance live events/session behaviour are configured and tested.

## Additional account/mail requirements captured

- Force Connect is only for a password-verified sign-in attempt when the incumbent session cannot be reached; it must recheck and refuse if the incumbent becomes reachable before takeover. The regular handoff flow remains for reachable sessions.
- My Computer shows `NONE` for First Bank account number until First Bank registration is complete. The server may reserve a number internally before then.
- In-game email is a major future feature with extensible `chainmail.net` / `badlook.com` domains, player/site/NPC identities, an era-style UI, 1,000-message mailbox cap, player messaging, levelled Spammer/Spammer Jammer and unlevelled Spammer Commander. Mailboxes, senders, attachments and spam events must be server-owned.
- Karmic-email attachments must use server-side actual payload metadata independent from the displayed filename/extension, because files may be disguised to trick players.
- Recovery-token schema exists as groundwork only. Reset delivery/verification/consumption is not implemented. Accounts lacking a verified external recovery channel need an independent recovery factor or documented secure manual recovery; the fictional mailbox alone is circular when a user is locked out of the game.


## Approved Stage 1 save-reset policy

The project owner explicitly accepts loss of existing legacy game-save data at this early development stage. The planned cutover discards/ignores schema-v1 `netshift_saves.save_data` and resets legacy browser-only gameplay/inventory state, rather than implementing a field-by-field legacy import. This does not authorize deletion of `netshift_users`, server-side bank/profile/canonical file/world records, or creation of transactions/purchases from client data. The reset must be one-time, transactionally marked, idempotent, and reject stale schema-v1 writes. Detailed contract and synthetic fixtures are in `NETSHIFT_STAGE1_MIGRATION_CONTRACT.md` and `scripts/fixtures/stage1-save-reset-cases.json`.


## Stage 1 Chunk 7 — canonical inventory view reconciliation
